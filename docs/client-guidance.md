# Glaux — Client Reference Guidance

This is guidance for anyone integrating Glaux into a wallet, on any
platform. The contract (`src/GlauxDelegate.sol`, `src/GlauxAccount.sol`,
`src/GlauxStorage.sol`, `src/lib/SignatureVerify.sol`) verifies signatures
and enforces a fixed 2-of-3 threshold; it knows nothing about platforms,
clouds, or key storage. Everything below is client responsibility, not
protocol behavior — where a claim depends on the contract, the function
that enforces it is named so it can be checked directly.

## F1 — the device factor

F1 is a P-256 key (`GlauxStorage.VERIFIER_P256`, `FactorSlot.data` encoding
`abi.encode(uint256 qx, uint256 qy)`), and it should be hardware-backed on
whatever device the user owns:

- Apple platforms: Secure Enclave, key non-extractable.
- Android: StrongBox if the device has it, otherwise TEE-backed keystore.
- Windows: TPM via Windows Hello.
- Any platform exposing WebAuthn: a raw P-256 key generated by the
  authenticator, used directly rather than through the WebAuthn assertion
  envelope (see the WebAuthn section below for why this is a *future*
  verifier type, not the current one).

P-256 is the primary verifier in Glaux for one concrete reason: it is the
only signature algorithm present in secure hardware across every consumer
platform, and it is also the only one with a live EVM precompile the
contract can call (`SignatureVerify._verifyP256` calls the
RIP-7212/EIP-7951 precompile at address `0x100`). No other algorithm
satisfies both constraints simultaneously today. Glaux is deliberately
platform-neutral: nothing in the contract or in this guidance ties F1 to
Apple, Google, or any single vendor, and integrators should preserve that
neutrality rather than hard-coding a single platform's key-storage API as
the only supported path.

## F2 — the paper factor

F2 is a secp256k1 key (`GlauxStorage.VERIFIER_SECP256K1`, `FactorSlot.data`
encoding `abi.encode(address)`) generated and handled as a cold, offline
factor:

- Generate it on a machine that is offline for the duration of generation,
  ideally one that is never connected to a network again (or is wiped
  immediately after).
- Print it. Do not store it in any form that touches a synced or networked
  device — no photograph, no cloud note, no password manager entry, no
  screenshot, ever, at any point in its lifecycle.
- Treat the printed copy as a bearer secret: physical possession is
  equivalent to signing capability, so store it as securely as the user
  would store a will or a physical safe-deposit key.
- F2 exists for recovery and for the rarer privileged operations, not for
  daily use — it should be signed with deliberately, never automated,
  never left connected to any signing service.

## F3 — the cloud co-signer

F3 is a secp256k1 or P-256 key held in software and synced through the
user's cloud provider of choice. The contract does not distinguish where a
factor's key material lives; conformance is a client responsibility against
three requirements: end-to-end encryption (the provider must not be able to
read the key material, only store and sync ciphertext the client controls),
authenticated access (the user's own authentication gates decryption, not
just account possession), and revocability (the user can invalidate that
copy of the key and rotate it out through `applyUpdate`'s
`ACTION_SET_SLOT`, without needing any other factor's cooperation from
the provider itself). iCloud Keychain, Google's equivalent secure sync,
and any generic E2E-encrypted storage backend all qualify against these
requirements — none of them is required and none is disqualified by name.

**Never Apple-only.** This is a hard project constraint, not a
preference: an integration that only offers an iCloud-backed F3 with no
alternative locks non-Apple users out of the third factor entirely and
contradicts the platform-neutrality this project commits to. Every client
must offer at least one non-Apple-only path to F3, even if iCloud remains
one of the supported backends.

## Birth

Birth follows the sequence in `GlauxDelegate.initialize` and the
`EIP-7702`/`GLAUX_INIT_V1` domain it checks:

1. Generate the ephemeral birth EOA client-side.
2. Sign the single EIP-7702 authorization tuple with `chainId = 0` — this
   is what makes the same tuple valid on every chain the account is later
   delegated on, present or future.
3. Sign the initialization blob: the digest is
   `keccak256(abi.encode(GlauxStorage.INIT_DOMAIN, implementation, keccak256(initData)))`,
   verified against `address(this)` as the signing key
   (`GlauxDelegate.initialize`'s call to `SignatureVerify.verify` with
   `GlauxStorage.VERIFIER_SECP256K1` and `abi.encode(address(this))`).
   `initData` decodes to the three `FactorSlot` entries — F2 at index 0,
   F1 at index 1, F3 at index 2 — so this is also the moment the three
   factor keys are committed to the account for the first time.
4. Destroy the birth key immediately once both signatures exist. There is
   no operation later in the account's life that needs it again, and its
   continued existence is pure risk (see the threat model's
   birth-environment-compromise residual).

**Deploy before you submit.** `GlauxDelegate.initialize` reverts with
`InvalidImplementation()` if `implementation.code.length == 0` — the logic
contract must actually be deployed on a given chain before the
initialization blob is submitted there. This fails safely: a premature
submission simply reverts, the signed blob itself remains valid, and it can
be resubmitted once the implementation is deployed on that chain, exactly
as any other update-replay-on-first-touch operation would be. Clients
should not rely on discovering the missing deployment only at submission
time, though — the failure is safe but still a wasted round trip. Verify
the implementation is deployed on the target chain before constructing and
broadcasting the transaction that calls `initialize`, not after.

## Never write the same key into two slots

`GlauxAccount.initializeAccount` and `applyUpdate`'s `ACTION_SET_SLOT`
branch both check every candidate slot against the other two via
`_isDuplicateSlot` (matching `verifierType` and identical `data`) and
revert with `DuplicateSlot()` on a match. This is enforced by the contract,
not merely recommended, but a client should never construct a slot
configuration that attempts it in the first place — presenting the user
with a transaction that is guaranteed to revert wastes a round trip and
signing effort for no benefit. Validate distinctness client-side before
asking the user to sign.

## Never sign two updates for one nonce

As detailed in the threat model's same-nonce-equivocation residual,
`applyUpdate` cannot detect that two different payloads have been signed
for the same `u.nonce` on different chains — its check is only
`u.nonce != l.updateNonce + 1`, evaluated independently on each chain's own
storage. The contract has no way to prevent this; the discipline is
entirely signer-side. A client must treat an update as consumed the instant
it is signed by the quorum, before it is observed on any chain, and must
never present the user (or an automated signing flow) with a second,
different update proposal at a nonce that has already been signed. If a
client's own state ever shows two signed-but-unconfirmed updates at the
same nonce, that is a bug in the client's own bookkeeping, not a contract
edge case to route around.

## Upgrades

`applyUpdate`'s `ACTION_SET_IMPLEMENTATION` branch decodes
`abi.decode(u.payload, (address, bytes32))` as `(newImplementation,
expectedCodeHash)` and requires both `newImplementation.code.length != 0`
and `newImplementation.codehash == expectedCodeHash`, plus a successful
`staticcall` to `glauxCompatibilityId()` returning
`keccak256("GLAUX_ACCOUNT_V1")`, before installing it. Practically, this
means:

- Compute `expectedCodeHash` from the contract actually deployed on each
  target chain — not from a local compilation artifact assumed to match,
  and not from one chain's deployment assumed to match another's. Read the
  code hash live from the chain the update will be submitted to.
- Verify that hash before asking the quorum to sign, since a single
  signed update, carrying no chain-id, installs that exact bytecode on
  every chain it reaches (see the threat model's code-hash-vs-behaviour
  residual for what this check does and does not guarantee about runtime
  behaviour once installed).
- Confirm the new implementation actually exposes
  `glauxCompatibilityId()` returning the expected constant before
  proposing the upgrade to signers, so a failing `applyUpdate` call is
  never the first time anyone learns the candidate implementation is
  incompatible.

## Update-replay reconciliation UX

Because the update channel carries no chain-id and replays "in order" on
each chain at first touch, a client must query `updateNonce` and the three
`FactorSlot` entries (`getSlot`, `updateNonce`) independently on every
chain it cares about and present the result honestly:

- A chain with a lower `updateNonce` than others is not broken — it simply
  has not yet received the more recent updates. Show it as "behind,
  pending relay," not as an error state, and let the user (or an automated
  relayer) submit the outstanding updates to catch it up.
- A chain never touched at all has no Glaux state whatsoever: the address
  there is a plain, undelegated EOA. Represent this plainly — "not yet
  active on this chain" — rather than silently omitting the chain from the
  UI or implying the account's configuration is already live everywhere.
- If two chains show the same `updateNonce` with different slot contents,
  that is the same-nonce-equivocation residual materializing, not a
  display bug: surface it as a conflict requiring a new quorum-signed
  update at a higher nonce to reconcile, per the recovery procedure in the
  threat model.
- Never present one chain's configuration as if it were a global,
  synchronized truth. The protocol does not provide a global view; the
  client's UI is the only place that can, and only by querying every chain
  it claims to represent.

## Gas

The account never needs a native balance for someone else to relay a
signed operation — `executeWithSigs` and `applyUpdate` are callable by
anyone holding a validly-signed payload, and the caller pays gas, not the
account. Under an ERC-4337 paymaster, an account can execute a userOp while
holding zero native balance: `test/EntryPoint4337.t.sol`'s
`test_userOp_sponsoredExecutionWithZeroBalanceAccount` deploys a
`TestPaymasterAcceptAll`, asserts `account.balance == 0` before and after a
successful `handleOps` call that executes a real call through the account,
proving sponsored execution requires no ETH held by the account at all.
Signatures authorize; the relayer or paymaster pays.

## WebAuthn as a future verifier type

The `(verifierType, data)` shape of `FactorSlot` (`GlauxStorage.sol`) is
designed to accommodate new signature schemes without moving funds or
changing the account's address: a new `verifierType` value, a new branch in
`SignatureVerify.verify` and `SignatureVerify.isValidKey`, and an
`applyUpdate` call rotating the relevant slot to the new type and key
material — the account's address, its other two factors, and its held
funds are untouched by the change. WebAuthn's full assertion format
(client data JSON, authenticator data, and the actual P-256 signature
bundled together, with the signed message being a hash of the client data
rather than the raw digest passed to `SignatureVerify.verify`) is a natural
candidate for such a future verifier type, distinct from the raw P-256 key
usage F1 uses today: it would let a client rely on a platform's native
WebAuthn ceremony end-to-end rather than extracting a raw key for direct
P-256 signing. That verifier is not implemented in Phase 1 — F1 today
signs raw digests directly with a P-256 key extracted through platform
APIs — but the slot design means adding it later is a scoped, additive
change, exactly like adding any other new verifier type, not a migration.
